# Техническое задание на разработку Omega Illustrator

**Документ:** техническое задание для реализации в Codex  
**Версия:** 1.0  
**Дата:** 02.11.2026  
**Статус:** согласованная проектная спецификация на основе тестового задания заказчика и предоставленного Figma  
**Тип результата:** локально запускаемый веб-сервис с возможностью серверного развёртывания  
**Стек:** C# / .NET 10 / ASP.NET Core / Blazor Web App (Interactive Server) / native SVG / минимальный JavaScript  
**Язык интерфейса:** русский  

## 0. Приоритет требований и принцип разработки

Разработать **реально работающий конструктор**, который автоматически компонует существующие векторные иллюстративные элементы и экспортирует итоговый **редактируемый SVG**. Не создавать генератор изображений и не подменять компоненты растровыми картинками или имитациями. Источником графики являются предоставленные работодателем элементы Figma.

Приоритет при конфликте требований:
1. Прямое исходное задание работодателя и его ограничения на изображения.
2. Установленные факты из исходного `.fig` и примеров композиций.
3. Эта спецификация реализации и выбранная архитектура.
4. Дополнительные удобства и расширения.

**Обязательный результат:** два сценария генерации, исходная библиотека SVG, S/L, три палитры, основной и фоновый тип предметов, автоматическая композиция, базовый ручной редактор, векторный экспорт, демонстрация, исходный код, описание архитектуры. **Дополнительное наше требование:** универсальная отдельная библиотека Omega AI Gateway с заменяемыми провайдерами. Расширенные провайдеры, сложные OAuth-интеграции, учётные записи и облачные сервисы не являются блокерами основных функций.

Не делать архитектурно избыточные микросервисы, собственную БД или React/Node/Python. Приемлемо небольшое число тщательно выделенных C#-проектов в одном решении.

## 1. Исходные материалы и правила использования

В комплекте предоставлены:
- `Тестовое _ иллюстрации.fig` – первичный файл Figma с заданием, графикой и образцами;
- `Figma_Illustration_Assets_Manifest.json` – подготовленный манифест распознанных графических групп и палитр;
- исходные скриншоты задания (для проверки текстовых ограничений).

По анализу файла Figma обнаружены пользовательские страницы `Cover`, `Задание`, `Библиотека компонентов`, `Примеры композиций`. Манифест описывает **10 предметных категорий** в четырёх комбинациях размера и роли (ориентировочно 40 групп для экспорта); реальные SVG нужно извлечь и верифицировать. Наличие в `.fig` векторных групп **не означает**, что внутри архива уже присутствует готовая библиотека SVG-файлов.

**Обязательные ограничения на исходники:**
- использовать только предоставленные иллюстративные объекты; нельзя дорисовывать предметы, использовать image generation и подменять их альтернативной графикой;
- сохранять оригинальную геометрию, детали, цвета/цветовые роли, целостность внутренних слоёв;
- запрещено менять пропорции объектов относительно друг друга, деформировать/разбирать внутренние части объектов; двигать и поворачивать цельный экземпляр можно;
- объект может быть главным (цветным) либо фоновым (монохромным); фоновые необязательны;
- три исходные цветовые схемы с возможностью добавления схем через данные;
- фоновые цвета могут использоваться в предметах, но цвета, предназначенные только для предметов, не могут использоваться в фоне;
- исходники использовать в рамках задания; до публичного коммита ассетов проверить право на распространение материалов заказчика.

Если экспорт из `.fig` в отдельные SVG не автоматизируется достоверно, реализовать каталог и импорт/инструкцию экспорта нужных групп. **Не заменять финальные элементы фальшивыми SVG.** Временные dev-заглушки допустимы только с явной маркировкой и полностью исключаются из финальной демонстрации.

## 2. Предметная область и каталог

### 2.1. Категории предметов

| Концепт (ID) | Название | Теги (примеры) |
|---|---|---|
| `book` | Книга | знания, обучение, чтение |
| `phone` | Телефон | связь, общение, коммуникация |
| `puzzle` | Пазлы | решение задач, идея, сборка |
| `coin` | Монета | деньги, финансы, ценность |
| `headphones` | Наушники | музыка, звук, прослушивание |
| `lamp` | Лампа | свет, идеи, работа |
| `flowers` | Цветы / букет | настроение, природа, забота |
| `wallet` | Кошелёк | деньги, оплата, накопления |
| `folder` | Папка | документы, порядок, организация |
| `pen` | Ручка | письмо, заметки, планирование |

Названия и семантика – программные метаданные. Реальные графические `assetId` и `figmaNodeId` брать из приложенного манифеста, перепроверяя спорные общие названия групп по визуальному содержимому.

### 2.2. Размеры и роли

Каждый предмет должен иметь варианты `S` и `L` (они отличаются детализацией, не простым масштабом) и роли `main`/`background`. При выборе размера **подменять весь источник SVG**, а не делать `scale(0.5)` одного большого файла. Координаты и поворот экземпляра при подмене сохранять в нормализованном виде, габариты – пересчитывать согласованно.

Для UI необходимы понятные переключатели размера и роли. Пользователь должен иметь возможность исключить фоновые предметы из композиции, не затронув главные.

### 2.3. Палитры

| Роль | Сиреневая | Персиковая | Бирюзовая |
|---|---|---|---|
| `bg1` | `#D7CDF5` | `#FDD7B9` | `#BEEBEB` |
| `bg2` | `#AA9BF0` | `#FAC896` | `#80DADA` |
| `bg3` | `#7864D7` | `#D27532` | `#5ABEBE` |
| `accent1` | `#F9ECB0` | `#F9ECB0` | `#FFD4F2` |
| `accent2` | `#F9A3AA` | `#80DADA` | `#6D7BFC` |
| `accent3` | `#FFE3E1` | `#BEEBEB` | `#B6C6FE` |
| `ink` | `#181817` | `#181817` | `#181817` |
| `white` | `#FFFFFF` | `#FFFFFF` | `#FFFFFF` |

Хранить палитры в расширяемом JSON или аналогичной конфигурации. Важно различать **семантические цветовые роли**, а не только HEX. В разных схемах некоторые значения повторяются: глобальная замена строк HEX недопустима, поскольку нельзя всегда однозначно восстановить смысл заливки. На этапе подготовки ассетов зафиксировать назначение слотов для каждой заливки/градиента (asset color mapping).

Правило валидации: цвета `accent1..3` **не должны попадать** в декоративный фон холста и монохромные фоновые объекты, если оригинальная схема не разрешает это явно. Цвета `bg1..3` могут применяться к объектам. Нейтральные `ink/white` сохраняют свою роль.

### 2.4. Фон оформления и фоновый предмет – разные понятия

`CanvasBackground` – фон холста, включающий при необходимости декоративные элементы исходной палитры. `background` у экземпляра предмета – монохромное изображение существующей книги/лампы и т. д. Эти сущности не смешивать в коде и UI.

## 3. Форматы и композиции

В исходном проекте представлены форматы:
- квадрат `1000 × 1000`;
- горизонтальный `1200 × 630`;
- вертикальный `800 × 1200`.

У пользователя должен быть выбор как минимум этих форматов; другие форматы могут добавляться декларативно, если это не нарушит композицию. В Figma есть 18 примеров композиций (по шесть для каждого формата) и шесть пробных образцов `SVG-drop` для S/L, демонстрирующих варианты `Собранно`, `Со смещением`, `Под заголовок`.

Реализовать три базовых шаблона:
- `clustered` – цельная группа главных элементов;
- `offset` – композиция смещена с сохранением баланса;
- `under-heading` – оставить безопасную пустую область под заголовок.

Шаблоны должны поддерживать три формата, S/L и количество объектов в разумных пределах; свободное пространство и приоритеты должны зависеть от формата. Допускается использовать дополнительные фиксированные layouts для улучшения качества, но без реализации новой графики.

## 4. Два обязательных сценария ввода

### FR-01. Генерация по заголовку или метафоре

Пользователь вводит свободный текст, например «Идеи для продуктивной учёбы». Программа анализирует смысл текста и выбирает **только зарегистрированные объекты** из каталога, подходящие роли и шаблон. Компоновщик размещает их автоматически.

Предпочтительный подход: AI Gateway отправляет запрос выбранной LLM, получает строго структурированный ответ в виде ID предметов и ролей. Сервис приложения проверяет разрешённые значения и независимо выполняет компоновку. Не принимать от LLM произвольные SVG/HTML/JS, новые предметы, инструкции изменения внутренней графики или небезопасные команды. При ошибке/отсутствии ИИ – объяснить состояние и предложить автоматический подбор по тегам, явно сообщив, что это упрощённый офлайн-режим.

Успех: при двух-трёх заведомо разных смысловых запросах выбираются осмысленные, объяснимые наборы существующих предметов; текстовые ошибки не ломают приложение.

### FR-02. Генерация по названиям предметов

Пользователь пишет `книга, лампа, телефон` либо выбирает предметы из каталога. Приложение нормализует написание и синонимы, разрешает ID, проверяет доступность соответствующих SVG и строит композицию без необходимости подключения нейросети.

При неизвестном названии показать конкретный неизвестный термин и список доступных предметов. Не подставлять произвольный иной рисунок. Порядок слов в исходном вводе может влиять на приоритет, но не должен запрещать ручную перестановку.

Успех: для корректного списка результат содержит ровно запрошенные предметные категории (если нет явного выбора фонового декора); не добавлять посторонние *главные* предметы.

### FR-03. Общие параметры генерации

Перед генерацией доступны: размер детализации `S/L`, формат холста, палитра, шаблон (`Авто` или явный), показывать/не показывать фоновые предметы. После генерации показывать готовый результат, а не пустой холст. Повторная генерация должна давать воспроизводимый результат при одном seed (полезно для тестирования). Если используется вариативность, хранить `seed` и выбранный алгоритм.

## 5. Графический редактор

### FR-04. Библиотека объектов

Панель каталога с названием, миниатюрой, типом/ролью и возможностью добавить предмет в текущую композицию. Для каждой записи известны `conceptId`, `size`, `role`, исходный `viewBox`, доступные темы, источник и семантические теги. Отсутствующий SVG не должен приводить к падению интерфейса; показывать причину и предлагать импорт исходника.

### FR-05. Операции на холсте

- выделить цельный предмет щелчком;
- перемещать его указателем/мышью;
- вращать вокруг центра (угол отображается и сохраняется);
- дублировать текущий экземпляр;
- удалять;
- перемещать на слой выше/ниже, наверх/вниз;
- переключать `main`/`background` с подменой соответствующего оригинального SVG;
- переключать S/L и палитру для всей композиции;
- отменить/повторить изменение (минимум базовая история в текущем сеансе – наше полезное дополнение);
- сбросить автокомпозицию / перестроить из тех же исходных предметов.

**Не разрешать:** редактирование внутренней геометрии, непарное изменение размера X/Y, произвольную замену цветов предмета в обход палитры, геометрическую деформацию и встраивание картинок в результат. Для осторожного прочтения ограничения о «пропорциях между объектами» **не вводить свободный независимый scaling отдельных предметов**; использовать согласованные коэффициенты масштаба сцены и размеры шаблонов.

### FR-06. UX и расположение

Один главный экран:
1. Верхняя панель: имя проекта, сброс/новая композиция, экспорт SVG.
2. Левая часть: вкладки `По смыслу` / `По объектам`, каталог, поле ввода, `Собрать`.
3. Центральная часть: SVG-холст с выделением и перетаскиванием.
4. Правая часть: формат, S/L, палитра, шаблон, фоновые элементы, список слоёв, свойства выбранного экземпляра.
5. Отдельная страница/модальное окно: `Подключение ИИ`.

Интерфейс на русском, с компактными понятными подписями. Должен работать в обычном Chromium/Edge на настольном компьютере. Адаптивная мобильная версия – необязательное улучшение, если хватает времени.

### FR-07. Производительность перетаскивания

Нативный SVG в DOM и локальный JS-модуль для `pointerdown/move/up`, расчёта pointer-to-SVG coordinates и трансформаций. **Не слать каждый `pointermove` через Blazor SignalR**, чтобы не создавать задержку при удалённом размещении. При завершении жеста синхронизировать одну завершённую операцию с C#-моделью. Учитывать zoom/transform матрицы, `getScreenCTM()`, CSS-скейлинг и браузерную историю pointer capture. При недоступной связи не повреждать сцену.

## 6. Алгоритм автоматической компоновки

### FR-08. Вход/выход компоновщика

Вход: `SceneRequest { conceptIds, roles, size, paletteId, canvasPresetId, layoutPresetId, seed }` и метаданные геометрии SVG.

Выход: `SceneDocument` со списком `SceneObjectInstance { instanceId, conceptId, role, normalizedPosition, rotationDeg, sharedScalePolicy, zOrder }`, фоном и ссылками на исходники.

### FR-09. Логика

1. Проверить входные IDs и доступность графики.
2. Определить форм-фактор и безопасные поля холста.
3. Выбрать и закрепить главные/вспомогательные предметы по смысловому приоритету.
4. Подобрать из разрешённых шаблонов позиции и согласованный масштаб.
5. Разрешить допустимые перекрытия, минимизировать непреднамеренные пересечения значимых контуров; сохранить текстовую безопасную зону в `under-heading`.
6. Рассчитать порядка слоёв (фоновая графика ниже главной, если специальный шаблон не требует иного).
7. Убедиться, что видимая часть композиции вписывается в холст, кроме явно предусмотренных дизайнерских обрезаний.
8. Вернуть редактируемый объект сцены, отображаемый на `<svg>`.

Нужно качество сопоставимых с предоставленными примерами композиций, а не «разложить всё в один ряд». Для небольшого набора (10 типов) допустим набор заранее настроенных layout-рецептов и детерминированные эвристики. Обучать модель для геометрии не требуется.

### FR-10. Инварианты

Выполнение любых пользовательских действий не должно менять локальную геометрию `path`/`polygon` исходного объекта. Разрешён только внешний `transform` группы целого предмета и подмена подготовленного SVG-варианта. Визуальные свойства палитры вычисляются из семантических токенов; изменения исходных `<path>` не записываются обратно в source assets.

## 7. Работа с исходными SVG и точный экспорт

### FR-11. Импорт/подготовка ассетов

- Получить корректные SVG каждого из вариантов из копии Figma; зафиксировать source node ID, `viewBox`, геометрические размеры, пути, hashes.
- Все вложенные пути, градиенты, маски, `clipPath`, фильтры и stroke сохранить, если они присутствуют и нужны.
- Преобразовать цвета в семантическое отображение, не заменяя их вслепую по совпадению HEX.
- SVG должен быть самодостаточным: без внешних ссылок на удалённые изображения и без JS.
- При загрузке стороннего SVG (если включена) принимать только ограниченные SVG элементы/атрибуты, исключить `<script>`, `foreignObject`, event handlers, опасные URI, внешний CSS и сетевые зависимости. Если корректное безопасное сохранение незнакомого SVG не гарантируется – не включать публичную загрузку в MVP.
- Подготовить отчёт импорта: исходный узел, вариант, результат валидации, количество найденных paths, ошибки/предупреждения.

### FR-12. Экспорт

На кнопке `Экспорт SVG` скачать реальный `.svg` со следующим логическим устройством:

```xml
<svg xmlns="http://www.w3.org/2000/svg" width="1200" height="630" viewBox="0 0 1200 630">
  <defs><!-- определения для градиентов, масок и клипов с уникальными ID --></defs>
  <g id="background"><!-- векторный фон и декор --></g>
  <g id="scene-objects">
    <g id="object-..." data-concept="book" transform="translate(...) rotate(...) scale(...)">
      <!-- реальные path/polygon/ellipse/line и вложенные группы оригинального SVG -->
    </g>
  </g>
</svg>
```

Пример показывает структуру, а не допустимость упростить реальную графику.

Обязательно:
- отдельная `<g>` на **каждый экземпляр** предмета, с внутренней векторной графикой, не растровым snapshot;
- сохранение порядка слоёв, фоновых декораций и цветовых схем;
- уникализация всех идентификаторов `id` при повторном использовании одного предмета, корректная замена всех ссылок `url(#...)`, `href="#..."`, `xlink:href`, clip-path/mask/filter/gradient; при необходимости поддержать style references;
- корректная экранизация XML и обработка SVG namespaces;
- отсутствие `<image href="data:image/png...">`, base64 PNG, canvas bitmap или общей «сплющенной» кривой вместо экземпляров;
- корректное открытие результата в браузере, Inkscape и импорт в Figma с сохранёнными отдельными группами;
- сохранение пропорций оригинальной графики, `preserveAspectRatio`/`viewBox`;
- визуальное соответствие экспортированного результата предпросмотру.

Поддерживать скачивание/сохранение `.scene.json` в дополнение к SVG – **полезное необязательное расширение**, не подменяющее обязательный SVG.

## 8. Универсальная «розетка» Omega AI Gateway (наше дополнительное требование)

### FR-13. Границы ответственности

Создать независимую C# class library `Omega.AI.Gateway`, не содержащую зависимостей на `OmegaIllustrator.Core`, SVG, сцены, палитры и Figma. Библиотека принимает унифицированные текстовые сообщения и возвращает результаты, нормализованные ошибки и метаданные использования; провайдеры реализуют транспорт/авторизацию.

**Преимущество:** тот же модуль можно будет подключить к другим проектам Omega Lab, не переписывая логику подключения моделей.

### FR-14. Минимальный интерфейс (ориентир, разрешается уточнять DTO)

```csharp
public interface IAiGateway
{
    Task<AiResponse> SendAsync(AiRequest request, CancellationToken ct = default);
    IAsyncEnumerable<AiStreamEvent> StreamAsync(AiRequest request, CancellationToken ct = default);
    Task<IReadOnlyList<AiModelInfo>> GetModelsAsync(string profileId, CancellationToken ct = default);
    Task<AiConnectionTest> TestConnectionAsync(string profileId, CancellationToken ct = default);
}

public interface IAiProvider
{
    string ProviderKind { get; }
    Task<AiResponse> SendAsync(AiProfile profile, AiRequest request, CancellationToken ct);
    IAsyncEnumerable<AiStreamEvent> StreamAsync(AiProfile profile, AiRequest request, CancellationToken ct);
    Task<IReadOnlyList<AiModelInfo>> GetModelsAsync(AiProfile profile, CancellationToken ct);
    Task<AiConnectionTest> TestConnectionAsync(AiProfile profile, CancellationToken ct);
}
```

DTO: `AiProfile(Id, Name, ProviderKind, BaseUrl, ModelId, AuthMode, SecretReference, Timeout, Enabled)`, `AiRequest(ProfileId, ModelId?, Messages, OutputMode, Options)`, `AiResponse(Text, ModelId, Usage?, FinishReason?)`, `AiModelInfo`, `AiConnectionTest`, `AiStreamEvent`, `AiGatewayException(ErrorKind, ProviderCode?, RetryAfter?)`.

Функции: несколько профилей одного/разных провайдеров, активный профиль, проверка соединения, ручной или динамический список моделей, корректные timeouts/cancellation, обработка 401/403/429/5xx, короткий retry только для безопасных отказов с учётом тарификации. Универсальный контракт должен допуска́ть различия возможностей моделей, а не обещать несуществующие универсальные функции.

### FR-15. Провайдеры и протоколы

**Обязательно для первой поставки:**
1. `OpenAiCompatibleProvider` для API, реализующих совместимый chat/response endpoint – URL, ключ при необходимости, modelId. Протестировать минимум один реальный облачный endpoint **или** один работающий локальный сервер.
2. `NoAi`/`RulesOnlySceneSelector` для сценария выбора объектов по тегам. Важно: офлайн-подбор находится **в доменной логике иллюстратора**, а не выдаётся за универсальную нейросеть.
3. `FakeAiProvider` для модульных тестов без оплаты.

**Далее – расширения без переписывания ядра:** `OllamaProvider`/LM Studio, Native Anthropic/Gemini adapters для несовместимых контрактов, официальный `ChatGptOAuthProvider`. Не считать все API буквально одинаковыми; для native контрактов писать adapters.

### FR-16. ChatGPT Plus и OAuth – опциональное подключение, не блокер сдачи

Обычный OpenAI API по ключу оплачивается отдельно от ChatGPT Plus. На дату составления спецификации OpenAI документирует `Sign in with ChatGPT` для поддерживаемых участвующих приложений, в том числе открытых/локально запускаемых клиентов, где при явном согласии пользователя может расходоваться доступный лимит подписки для допустимых Responses API-запросов. Это **не** универсальный «API-ключ из подписки».

Если реализуется адаптер:
- использовать только официальный поддерживаемый OAuth/OIDC с `state`, `nonce`, PKCE, валидацией ID token/JWKS, проверкой выданных scopes и безопасным хранением/обновлением токенов;
- авторизация – системный браузер и loopback callback, без запросов пароля и без чтения cookies ChatGPT;
- пользователь явно подтверждает использование allowance/лимита; при отказе или отсутствии нужного scope не отправлять AI-запросы;
- учитывать поддерживаемые модели, endpoint, streaming и ограничения официальной интеграции; не утверждать, что получится запуск любой модели;
- при невозможности подключения показывать понятную причину и предлагать обычный API/local LLM.

Документация: https://developers.openai.com/siwc/token-sharing-open-source ; https://developers.openai.com/siwc/token-sharing-open-source/sign-in ; https://help.openai.com/en/articles/6950777-what-is-chatgpt-plus . Для платного удалённого сервиса может потребоваться отдельное участие/одобрение – не внедрять OAuth на недопустимой схеме развёртывания.

### FR-17. Слой выбора элементов на основе ИИ

В `OmegaIllustrator.Core` определить `SceneSuggestionService`:
1. Получает тему, текущий каталог и пользовательские ограничения.
2. Формирует запрос с конечным whitelist `conceptId`.
3. Вызывает `IAiGateway`.
4. Десериализует ответ в строго типизированную структуру:

```json
{
  "objects": [
    {"conceptId": "book", "role": "main"},
    {"conceptId": "lamp", "role": "background"},
    {"conceptId": "puzzle", "role": "main"}
  ],
  "layoutPresetId": "under-heading"
}
```

5. Применяет white-list ID, whitelist ролей, whitelist шаблонов, ограничения по числу объектов, проверяет доступность S/L и графику; игнорирует любые дополнительные поля команд/кода/произвольных URL.
6. Передаёт разрешённый набор в локальный `CompositionEngine`, который **сам** рассчитывает координаты и формирует SVG. Ни один ответ модели не вставлять в DOM как произвольную разметку.
7. При ошибке JSON – ограниченная одна корректирующая попытка (если экономически/технически оправдана) либо явный fallback по тегам с сообщением в интерфейсе.

### FR-18. Страница AI-настроек

- Выбор режима: Без ИИ / API / Local / ChatGPT (при поддержке).
- Добавление/редактирование/удаление профиля, имя, endpoint, модель, ключ/авторизация.
- Кнопки `Проверить подключение`, `Получить модели`, `Сохранить`, `Подключить/Отключить`.
- Состояния: готово, отсутствует соединение, истёк ключ, нет разрешения, лимит, невалидный ответ.
- Значение API-ключа никогда не возвращать UI после сохранения; показывать только «ключ сохранён».
- Логи обращений без токенов и без конфиденциального содержимого. Usage/стоимость показывать только если провайдер реально вернул эти данные; не выдумывать лимиты ChatGPT.

```text
│  ├─ OmegaIllustrator.Web/           Blazor Web App, Kestrel, UI, thin API endpoints
│  │  ├─ Components/Pages/
│  │  ├─ Components/Editor/
│  │  ├─ Services/

│  │  └─ Program.cs

│  │  ├─ Assets/
│  │  ├─ Composition/
│  │  ├─ Palette/
│  │  ├─ Svg/
│  │  └─ Semantic/
│  ├─ Omega.AI.Gateway/               Универсальные DTO, интерфейсы, маршрутизация
│  └─ Omega.AI.Providers/             Адаптеры OpenAI-compatible / local / доп.
├─ assets/
│  ├─ svg/S/main/; svg/S/background/
│  ├─ svg/L/main/; svg/L/background/

│  ├─ ASSETS.md
│  ├─ DEMO.md
│  └─ AI_TOOLS.md
└─ README.md
```

Разрешается объединить провайдеры в одной library при небольшом объёме проекта; **не дублировать** общую логику транспорта и DOM/SVG. Зависимости односторонние: Web → Core и Gateway; Core может обращаться к **абстракции** Gateway для смыслового подбора, но Gateway ничего не знает о Core; реализация провайдеров зарегистрирована через DI в Web. Ещё лучше передать `IAiTextService` через адаптер приложения и не привязывать Core к конкретной транспортации.

**Хранилище:** JSON и файлы в пользовательской папке данных, а не рядом с кодом в `wwwroot`. Публикуемый статический каталог – только безопасные графические ассеты. Настройки/история сцены хранятся отдельно, конфиденциальные секреты – в OS secret store (локально Windows DPAPI/Credential Manager, на сервере environment/secret manager). База данных и регистрация не нужны для тестового.

Одного локального режима с видео достаточно, если публичная демонстрация недоступна.

## 11. Безопасность, надёжность, тестируемость

### NFR-01. Безопасность SVG
Не запускать скрипты из SVG; нормализовать/проверять SVG XML, запрещать XXE, внешние ресурсы, `foreignObject`, небезопасные ссылки, скрипты, обработчики событий. При невозможности полной санитизации произвольного пользовательского SVG **не включать его импорт в публичную версию**. Убедиться, что экспорт не внедряет опасную разметку.

### NFR-02. Безопасность ИИ и ключей
Ключи/tokens хранятся серверно, не в браузерном `localStorage` и не в Git. Для localhost HTTP – использовать только действительно локальные URL, для внешних – HTTPS и проверку endpoint. Защитить от SSRF на серверном развёртывании. Разрешённые модели и провайдеры проверять; никаких произвольных shell-команд по ответу ИИ.

### NFR-03. Надёжность
Отсутствующие ассеты/провайдер/интернет – понятное сообщение и сохранение предыдущей сцены. Не уничтожать готовую композицию из-за ошибки нового запроса. Все длительные операции поддерживают `CancellationToken` и таймаут. Избегать бесконечных повторов запросов, особенно платных.

### NFR-04. Скорость
После загрузки приложения ручное выделение/перемещение/вращение на типичном ПК должны ощущаться плавно; не перерисовывать весь Blazor component tree на каждое перемещение. Повторное использование SVG не должно создавать ID-коллизии. Показать корректный статус при длительном обращении к ИИ.

### NFR-05. Автотесты
Обязательны xUnit unit/integration tests для каталога, вариантов S/L, палитр, scene model, layout с seed, whitelisting ответа ИИ, экспорта 2 экземпляров одного SVG и ошибок адаптеров. Автоматическая проверка XML синтаксиса SVG и отсутствия растровых/опасных элементов. При наличии возможности добавить браузерные smoke-тесты (не требовать Playwright/Node, если это создаёт ненужные зависимости).

### NFR-06. Чистота проекта
Nullable reference types, DI, стандартное логирование `ILogger`, понятные ошибки, отсутствие API-ключей в репозитории, `.gitignore`, README, CI build/tests при возможности. Избегать крупных универсальных фреймворков, не относящихся к задаче. Явное разделение инфраструктуры и доменной логики.

**Дополнительные приёмочные тесты Gateway (не заменяют AT-01–AT-20):**

- OAuth (если реализован) запускается официально и проверяет scopes, не требует пароля ChatGPT;
- API ключ не появляется в HTML, JS, JSON scene, логах или экспортируемом SVG.

1. Работающая ссылка на веб-сервис **или** запускаемый проект с коротким видео/скринкастом.
2. Репозиторий исходного кода без секретов и с корректными правами доступа к ассетам.
3. Краткая архитектурная схема: где лежат SVG, как выбираются предметы, как разруливаются цветовые роли, как собирается сцена, как экспортируется редактируемый SVG.
4. Перечень **реально использованных** AI-инструментов в процессе разработки (например, ChatGPT/Codex/провайдер – только если фактически применялись).
5. Два-три примера собранных композиций, в том числе демонстрация разных палитр и форматов.

## 15. Обязательная итоговая документация Codex

- `README.md` – назначение, системные требования, команды запуска/publish, краткое демо.

- `docs/ASSETS.md` – происхождение SVG, ID, S/L, роли, как добавлять новые предметы, status экспорта.
- `docs/AI_TOOLS.md` – инструменты, применённые при разработке, не придумывать.
- `docs/DEMO.md` – пошаговый сценарий демонстрации по двум режимам и экспорту.
- `docs/TESTING.md` – unit/integration/smoke tests и результаты исполнения.
- `docs/KNOWN_ISSUES.md` – только реальные оставшиеся ограничения/вопросы, особенно при неполных SVG.

## 16. Явные запреты для Codex

- Не уходить в бесконечное проектирование – после анализа приступить к реализации, сборке и проверкам.
- Не заявлять, что приложение готово, если оно не собирается или графика в финальном сценарии подменена заглушками.
- Не использовать стороннюю графику вместо объектов заказчика.
- Не считать PNG/Canvas изображение «векторным SVG» только потому, что оно вложено в контейнер `<svg>`.
- Не заставлять пользователя оплачивать API для базового редактора и ручного выбора объектов.
- Не вставлять API-ключи, cookies или OAuth-токены в клиентский код и Git.
- Не пытаться использовать ChatGPT Plus через неофициальный парсинг веб-интерфейса/внутренние endpoints.
- Не усложнять проект Docker/Kubernetes/БД/очередями без объективной необходимости.
- Не считать расширенные AI-провайдеры важнее обязательных требований заказчика.

## 17. Что должен делать Codex после получения ТЗ

1. Прочитать документ целиком, изучить исходный `.fig` и `Figma_Illustration_Assets_Manifest.json`.
2. Создать минимально достаточный `OmegaIllustrator.sln` на .NET 10 и скелет папок.
3. Проверить возможность получить/подключить **реальные** SVG по ID из манифеста. Если экспорт требует ручного Figma – дать список точных групп и инструкцию; параллельно реализовать независимые от ассетов модули.
4. Выполнить этапы 1–5, после каждого прогнать `dotnet build` и `dotnet test` и исправить ошибки.
5. Проверить реальные композиции, SVG-повторное открытие, повторяющиеся `defs`/IDs, S/L, палитры и оба сценария.
